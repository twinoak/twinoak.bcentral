## Decisions taken

- **The task file as on disk, not as committed, was built** (note at the top): the clock-trust
  item was added to the task during the run and is implemented; the rest of the task text was
  not changed.
- **The strip shows the current run; the history shows everything.** A message that was
  given up and retried by hand reads `sent 20:05 · delivered 20:05`, not the whole saga; the
  earlier run is one History click away. The run boundary is a `sent` that does not follow
  another `sent` — a contract-level rule (text-protocol.md: "A message can go back from
  `given_up` to `sent` by a manual retry"), no text is parsed.
- **"waiting" is the strip's last segment whenever the latest status is `sent`**, with the
  latest `sent`'s text in brackets when it has one ("waiting (attempt 2/3)"). The attempt
  text is displayed, never parsed. While the outbox or the queue holds the message, its own
  progress text ("attempt 2/3, waiting for the receipt", "waiting for its turn") replaces the
  segment, so the row says the same thing the queue screen says.
- **A `status_change` is a row only when it refers to the incident itself** (`refersTo ===
  incidentId`: closed / reopened — an event of the incident, and the acceptance's "1 incident
  close"). One that refers to a `message_out` in the list is that message's history. One
  whose referent is neither (an orphan, only possible in imported data) is not shown at all:
  the task says never a row, and there is no row to fold it into; it stays in the data and
  the export. Flagged under *Follow-ups*.
- **The old resend `note` is recognised by its `refersTo` pointing at a `message_out`**, not by
  its text: that is the only kind of `note` with `refersTo` the app has ever written, and the
  schema allows it. It is listed in the history and ignored by the strip (it is not a status
  change). A later feature that writes a `note` with `refersTo` (the P0-07 follow-up about
  linking "vedr. #12" replies) would land in the history too; decide then.
- **The attempt text goes through `t()`** (`send.text.attempt`, "attempt {attempt}/{max}"),
  like every other text the outbox stores ("round trip {ms} ms", "no ack after …"). The task
  spells it `attempt 2/3`; that is the English catalog's value. Storing UI-language text in
  the journal is the existing practice; worth a decision before the hub merges journals from
  devices in two languages (*Follow-ups*).
- **Batch counters count what each recipient reached in its current run**: `sent` = the strip
  has a `sent`, `delivered` = has `delivered`, `roger` = has `roger`, `given up` and `pending`
  = the current status. So `25 sent · 23 delivered · 18 roger · 1 given up` adds up the way
  the task's example does (the given-up one was sent first). Zero counters are not shown.
- **The batch's state is the slowest recipient's: `given_up` if any has given up, else the
  least advanced along pending < sent < delivered < roger.** A given-up recipient needs a
  hand, so it outranks "slow". The chip and the colour follow it.
- **Recipients inside a batch stay in transmission order**, and so do the rows of a batch on
  the queue screen: they are a list of people the text went to, not events; the queue's
  order is what goes out next. Batches themselves are newest first on both screens. The
  history of one message is oldest first, the order the strip reads in.
- **The history disclosure is per recipient only** (the task's open point): a batch has no
  transitions of its own, and a batch-wide list would interleave 25 chains. The batch row
  opens into its recipients; each recipient row has its own History.
- **"Last heard from" stays quietest first** (the task's lean): it exists to show who has
  gone quiet. Said in the code and the test name.
- **Open items: newest first within a group, and the groups by their newest item.** The task
  lists the panel under "newest first everywhere"; the label sort went. The cost is that the
  most overdue item sinks to the bottom — *Open questions*.
- **The "N new" count is the rows that were not on the timeline when the operator scrolled
  down**; the viewport itself is kept by CSS scroll anchoring (`overflow-anchor: auto`,
  Chromium's default, set explicitly) rather than by script. Manual check pending.
- **`enqueue` returns the batches it touched and merges into a batch the session already
  holds** (same `batchId`), so a straggler found by `requeuePending` after an incident change
  joins its batch instead of making a second row with the same id. `requeuePending` returns
  `[]` instead of `null` when nothing is pending.
- **A single send that is still pending after a reload is a batch of one**, keyed by its
  message id, as before in substance (P0-08 queued it in the restored batch); the queue
  screen's title says "1 recipient".
- **The batch `batchId` is minted with the store's monotonic ULID factory** (exported as
  `mintId`), not a second `ulid` instance, so ids minted in the same millisecond stay ordered.
- **The clock-trust mark**: `?` dimmed for `unknown`, `✓` green for `manual`, nothing for
  `ntp`; the top bar carries the one sentence while the session's clock is unconfirmed, as a
  link to the settings page. `clockTrust()` is session state already (`lib/clock.svelte.ts`),
  so nothing new is stored.
- **No dependency added. `contract/` untouched** (`batchId` was added on 2026-10-29 before
  this task). Prettier was run on the files that were already formatted (`journalView.ts`
  and its test, `Timeline.svelte`, `OpenItemsPanel.svelte`, `sendQueue.svelte.ts` and its
  test, `manual.test.ts`); `TopBar.svelte`, `types.ts`, `outgoing.ts`, `outbox.svelte.ts`,
  `journalStore.ts` and their tests were unformatted before and are left so.
- Candidates for `docs/decisions.md` (the four 2026-10-29 rows already cover the task's
  core): the strip shows the current run; batch state = slowest recipient, given up first;
  recipients in transmission order inside a newest-first list; the history disclosure is per
  recipient.

## Follow-ups

- [ ] A `status_change` whose message is not in the loaded list is not shown anywhere on the
      screen (the task's "never a row"). It cannot be produced by the app, only by imported
      data; when a merge/restore path arrives (phase 2), decide whether such entries should
      surface somewhere (a "stray entries" count on the incident bar, say).
- [ ] `contract/text-protocol.md` still says the batch id is "not part of the exchanged
      data"; since 2026-10-29 `batchId` is in the schema. Out of scope here (the task forbids
      touching that file); one line to fix in a `tasks:`/contract commit.
- [ ] Journal texts the app stores are in the UI language (`send.text.attempt`, `round trip
      …`, `no ack after …`, `no radio connected`). Fine for one PC; decide before the hub
      merges journals from devices with different languages (store English, or a code).
- [ ] The open-items panel is newest first, so the most overdue item is at the bottom. If the
      walkthrough shows operators scanning for the oldest, an "oldest open first" toggle or
      an age mark per item would help (see *Open questions*).
- [ ] Corrections of corrections are not shown (as before P1-01: they nest one level only).
- [ ] The timeline is still not windowed; a batch of 25 opens into 25 rows, a drill with ten
      batches is a long page (P0-07 / P0-08 follow-up stands).
- [ ] No component-level tests (as before): the pill, scroll anchoring, the disclosures and
      the strip's in-flight replacement are exercised by hand only.
- [ ] `queue.item.earliest` / drain-time estimate and the other P0-08 follow-ups are
      untouched.
- [ ] The stored `pending` entries in `contract/examples/walkthrough.json` could be removed
      from the example now that the app never writes them; kept here because the acceptance
      wants an old journal with them to render identically.
- [ ] Prettier: `TopBar.svelte`, `types.ts` and the P0-02 to P0-06 files are still
      unformatted (`npm run format:check`); one `npm run format` commit after the phase.
- [ ] `docs/decisions.md` candidates listed under *Decisions taken*.
