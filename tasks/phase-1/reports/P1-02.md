## Done

Answering an incoming message is one click or one key. Every `message_in` row has **Reply**;
it fills the compose form with the sender and the transport the message came in on, puts the
cursor in the text, and the sent message carries `refersTo` = the incoming entry's id. The two
rows then point at each other.

- `store/outgoing.ts` (P0-05 file) — `ComposeInput.refersTo?`: the incoming entry's id;
  `composeMessage` reads the target from the store first and throws `ReplyTargetError` when it
  is missing or not a `message_in` (nothing is reserved, the `#n` counter is untouched), then
  stores the `message_out` with `refersTo`. `replySnippet(text, max = 60)` is the "Replying
  to" line's text: the first 60 characters (code points, so a Danish letter or an emoji is
  never split) with `…` when cut. `store/types.ts`: `refersTo?` on `NewMessageOut`.
- `store/journalView.ts` (P1-01 file) — `MessageView.answers`: the `message_in` the message's
  `refersTo` points at, when it is in the list and is a `message_in`, else `null`. An `entry`
  row gets `answeredBy`: the `message_out` entries whose `refersTo` is this entry, oldest
  first. Both are read off `refersTo` on every build; nothing new is stored. `findRow` already
  finds both ends, so each mark can scroll to the other.
- `components/ComposeForm.svelte` (P0-05 file) — exports `replyTo(entry)`: sets the recipient
  to the entry's `counterpartyId` and the transport to the entry's transport, keeps a
  `replying` state, scrolls the form into view (`scrollIntoView`, nearest, smooth) and focuses
  the text. While replying a line "Replying to: ‹snippet›" (`role="status"`,
  `data-replying-to` = the id) sits between the recipient row and the text with a ✕ button
  (`aria-label`/`title` "Drop the link to the incoming message (Esc)"). Send passes `refersTo:
  replying?.id` and clears the link after a successful send; a failed send keeps it. One
  `onkeydown` on the form: **Esc** drops the link when one is set (and only then; the fields
  keep their values), **Ctrl+Enter** sends when the form may send (`canSend`). A small
  "Ctrl+Enter sends" hint sits beside the button.
- `components/Timeline.svelte` (P1-01 file) — new prop `onreply`. Incoming rows get a
  **Reply** button (primary style, before Correct), `tabindex="0"` and an `onkeydown` that
  calls `onreply` on `R`/`r` with no modifier, only when the row itself has the focus

## Decisions taken

- **The reply's target is checked in the store path**: `composeMessage` refuses a `refersTo`
  that is not a stored `message_in`. The schema allows any entry id in `refersTo`; this is
  not a new rule about the data but an integrity check on the one thing the app writes there
  (text-protocol.md: a reply "records a `refersTo`"). Not atomic with the write (two
  transactions): entries are immutable, so a `message_in` that was there a moment ago still
  is.
- **The transport follows the incoming message**, as the task says, and the operator may
  change it in the form before sending; the store does not check that the reply's transport
  matches the incoming one (a courier note may well be answered by radio).
- **`R` reacts only when the row itself has the focus.** The row is focusable
  (`tabindex="0"`); a key pressed in the Reply or Correct button inside it, or in a form row
  under it, is not the row's. Modifier combinations (Ctrl+R = reload) are left to the
  browser. Esc and Ctrl+Enter are one listener on the compose `<form>`; nothing is attached
  to `window` or `document`, so nothing else on the page reacts. Svelte's
  `a11y_no_noninteractive_element_interactions` on the form is silenced with a comment that
  says why; the row's `tabindex` is a dynamic attribute and raised no warning.
- **Esc drops the link and nothing else**: recipient, transport and typed text stay. The task
  says "drops the reply link"; emptying the text would lose work.
- **A failed send keeps the link**, so the operator can fix the cause (no radio, too long)
  and send the same reply; a successful send clears it along with the text. Choosing another
  incident re-creates the form (`{#key current.id}`), which also clears it.
- **Several answers to one incoming message are all shown**, oldest first, each its own
  "answered ‹time›" link: the data allows it and the second answer is as real as the first.
- **"Recipient rows of an expanded batch when they are incoming replies"** (task scope):
  after P1-01 no incoming message is ever nested inside a batch row — the recipient rows are
  the batch's `message_out` entries, and every `message_in` is a row of its own with its
  Reply. So there was nothing to add there; a batch recipient that itself carries `refersTo`
  shows the "↳ answers" mark like any message (tested). The roger history lines resolve the
  incoming "R1" but got no Reply: one answers the free-text message, not the roger.
- **Open-items panel**: it lists `message_out` entries only (not yet roger), never an incoming
  row, so the "same Reply affordance on incoming rows it lists, if any" is moot — the task's
  own "if any". Nothing changed there.
- **The "↳ answers" mark on the message row, "answered" on the incoming row**, both under the
  text in the strip's size, each a link button with the other text as tooltip; the mark is
  above the strip so the strip keeps reading as one line.
- **The snippet counts code points, not UTF-16 units or bytes**: 60 "characters" as a human
  counts them. Whitespace is kept as it is (no collapsing: nothing fuzzy).
- **A "Ctrl+Enter sends" hint** beside the Send button: a shortcut nobody can discover is not
  a shortcut; one short key. Esc is explained on the ✕ button's label/tooltip. P1-09
  (keyboard shortcuts for compose/send/roger) may move or restyle these.
- **No dependency added. `contract/` untouched.** Prettier was run on `journalView.test.ts`
  (formatted before); `Timeline.svelte` and `journalView.ts` were formatted and still are;
  `ComposeForm.svelte`, `JournalPage.svelte`, `outgoing.ts`, `types.ts` and the other tests
  were unformatted on `main` and are left so (P1-01 follow-up: one `npm run format` after the
  phase).
- Candidates for `docs/decisions.md`: a reply is `refersTo` on the `message_out` (the
  incoming entry is never touched); the store refuses a reply to anything but a stored
  `message_in`; the answered link is derived both ways, never stored.

## Follow-ups

- [ ] No component-level tests (as before): the prefilled form, focus, scroll, ✕, and the
      three keys are exercised by hand only. A Svelte component test harness (vitest +
      jsdom or browser mode) would cover P1-01's pill and this task's keys in one go; a
      dependency decision.
- [ ] The incoming row's `tabindex="0"` makes every incoming row a tab stop; with hundreds
      of rows, tabbing through the timeline is long. P1-09 (operator ergonomics, keyboard
      shortcuts) should decide on a roving focus (arrow keys between rows, one tab stop).
- [ ] The text-protocol says the operator "can link [a `vedr. #12` reply] to #12 by hand,
      which records a `refersTo` on the incoming entry" — the opposite direction (incoming →
      outgoing), and impossible after the fact since entries are immutable (the inbox writes
      the `message_in` before the operator sees it). The only link the app can record is the
      one this task writes (outgoing → incoming). Propose a one-line fix to
      `contract/text-protocol.md` in a `tasks:`/contract commit, or a design for linking an
      incoming message to the order it answers (a `note` with `refersTo`?) — see *Open
      questions*.
- [ ] The "Replying to" snippet shows the first 60 characters of the raw text; a long text
      with a line break shows the break. Fine until someone complains.
- [ ] "Ctrl+Enter sends" sits beside Send in every language; on macOS the key is still Ctrl
      (the handler ignores Meta). P1-09 may want ⌘.
- [ ] Prettier: `ComposeForm.svelte`, `JournalPage.svelte`, `outgoing.ts`, `types.ts` and
      their tests remain unformatted (P1-01 follow-up stands).
- [ ] `docs/decisions.md` candidates listed under *Decisions taken*.
