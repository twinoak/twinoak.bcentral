- **Transports keep their device** (`radio/serial.ts`, `radio/ble.ts`). `FrameTransport`
  gained `device`: the `SerialPort` or `BluetoothDevice` behind the link, null until the
  chooser has picked one, kept across `disconnect()`. `MeshCoreSerial` takes
  `{ serial?, port? }`: a port given (from `getPorts()` or a `connect` event) is opened with
  no chooser; a port chosen once is reopened by the next `connect()`; `disconnect()` closes
  the port only if it was open. `MeshCoreBle` takes `{ bluetooth? }`, keeps the chosen device
  for the session and calls `device.gatt.connect()` again on the next `connect()`; the
  `gattserverdisconnected` listener stays on the device. Both default to the navigator's
  API, so tests pass fakes. The `isSupported()` statics are gone (see `capability.ts`).
- **The store** (`radio/radioStore.svelte.ts`), new in its API:
  - `disconnectReason()`: `unplugged` (the USB `disconnect` event), `lost` (the read loop
    ended over USB with no event), `bleLost` (GATT gone), `silent` (no answer to the link
    check), `gaveUp` (the Bluetooth loop ran out of time); null after a manual disconnect and
    once connected again. `disconnectReasonText()` renders it through `t()`.
  - `reconnecting()` → `{ attempt, nextAttemptAtMs }` while the loop runs,
    `reconnectCountdownMs()` on the store's one-second tick, `canReconnect()` (a transport
    with a device is kept), `reconnectNow()` (wakes a waiting loop, or starts one on the kept
    transport), `verifyLink()`, `clockDriftSeconds()`, `start()`.
  - **The reconnect loop.** One plain async function: wait `RECONNECT_DELAYS_MS`
    (`[2000, 5000, 10000, 30000]`, the last repeating), attempt, repeat. It starts when the
    read loop ends on its own (`closedByLink`), when the link check fails, when a granted USB
    port's `connect` event arrives (first attempt at once), and on `start()` (same). Each
    attempt over USB looks the port up again: the kept port when `getPorts()` still lists it,
    else the one granted port (so a radio the browser hands back as a new `SerialPort` object
    is connected all the same), and none or several ends the loop with a log line — a plug
    event starts it again. Over Bluetooth every attempt is the kept device, and the loop
    gives up when the next attempt would fall past `BLE_RECONNECT_GIVE_UP_MS` (5 min) since
    the loss: reason `gaveUp`, device kept, Reconnect starts a fresh loop with a fresh
    budget. A manual `connect()` or `disconnect()` bumps the loop's token; the loop sees it
    at its next await and stops. The wait is one `setTimeout` on a `deferred`, so
    `reconnectNow()` and a cancel end it early.
  - **USB events.** `start()` listens on `navigator.serial`: `disconnect` of the kept port
    (another known port is somebody else's) while connected over USB tears the link down with
    reason `unplugged` and ends any loop (the port is gone; retrying is pointless until it is
    back); while already disconnected it just sets the reason. `connect` starts the loop
    when the store is disconnected, unless a Bluetooth loop is running. The event's target is
    not compared on `connect` (see *Decisions*).
  - **Wake.** `start()` also listens for `visibilitychange` (when visible), `resume`,
    `pageshow` and `online` (`PageEvents` dep: document, window, `isVisible()`), each running
    `verifyLink()`: `companionGetTime` with `LINK_CHECK_TIMEOUT_MS` (3 s); an answer counts as
    heard; no answer tears the link down with reason `silent` and starts the loop with an
    immediate first attempt.
  - **Clock drift.** On every connect the existing clock sync's `before − requested`
    (companion minus PC, seconds) is kept as `clockDriftSeconds()`; beyond
    `CLOCK_DRIFT_LIMIT_S` (60) a line `clock drift: companion was N s ahead of/behind the PC
    (limit 60 s); the journal keeps the PC's clock` is logged. Nothing about clock trust or
    the journal's stamps changes.
  - Log lines for every step, through the same `log()` (stamped, last 200, newest first on

## Decisions taken

- **The transport keeps the device; the store keeps the transport.** The task says the BLE
  device object is kept for the session; the same shape serves USB (a `SerialPort` can be
  reopened) and gives one reconnect path for both: `kept.connect()` again. The alternative,
  a store that holds raw `SerialPort` / `BluetoothDevice` objects and builds transports
  around them, would put browser objects into the store for no gain. `FrameTransport.device`
  is typed `EventTarget` (both browser objects are one) so the store needs no cast.
- **`disconnected` with a reason, not a fifth state.** The task's wording ("state →
  `disconnected` with the reason"); the top bar and the queue's pause rule keep working
  unchanged, and the loop's position is a second reading (`reconnecting()`), not a state.
  During an attempt the state is `connecting` as for a manual connect.
- **A lost link always starts the loop, also over USB.** The task's unplug path is: event →
  `disconnected` → `connect` event → reconnect. A companion that reboots without the OS
  seeing a replug, or a read error with the port still present, has no event; so the loop
  starts on any lost link and its first USB attempt asks `getPorts()`: port gone → stop and
  wait for the plug event (one log line), port present → retry with the task's backoff. The
  `disconnect` event, when it comes, ends the loop (nothing to retry) and sets the reason.
- **The `connect` event's target is not compared with the kept port.** Chromium may hand out
  a new `SerialPort` object for the same radio after a replug (the port's token changes);
  comparing would leave a replugged radio unconnected. The attempt resolves the port by
  presence instead: the kept one if `getPorts()` still has it, else the one granted port.
  The `disconnect` event does compare, so another granted port's unplug is ignored. One
  radio at a time is the task's scope.
- **Only losses reconnect automatically.** A manual connect that fails (chooser cancelled,
  not a companion) shows its error and starts no loop; the operator is there.
- **USB retries forever while the port is present; Bluetooth gives up after 5 min**, as the
  task says for each. The USB case is harmless (one `open()` every 30 s, logged) and ends
  by itself when the port is unplugged. No "stop" button; a manual Connect or Disconnect
  ends the loop (*Follow-ups*).
- **The reconnect budget is measured by the store's clock**, not by counting delays, because
  an attempt itself takes time (a GATT connect can take ten seconds); the check is "would
  the next attempt start after the budget".
- **Wake events: `visibilitychange`, `resume`, `pageshow`, `online`.** The task names the
  first and "`online`/`resume`-like events"; `pageshow` covers a back-forward-cache restore,
  `resume` the Page Lifecycle freeze. A check while disconnected does nothing (the loop or
  the operator owns that); overlapping checks are serialised by the link's command lock.
- **Drift is companion minus PC before the sync**, from the `companionSetTime` result the
  store already had, so no extra command goes over the link; the sign tells the page whether
  the firmware corrected it (behind → set forward) or kept it (ahead). The limit is a
  constant, not a setting.
- **The reconnect timing is a dep** (`reconnect?: ReconnectTiming`) so the loop is tested in
  milliseconds with real timers, the way the outbox tests shorten the ack window; the real
  constants are asserted in their own test. Fake timers were considered and dropped: they
  would also fake the link's own timeouts and the fake serial port's streams. Two first
  drafts of the tests polled for a phase that lasts milliseconds and flaked under load; the
  tests now look at a phase that lasts (a 10 s first delay, a GATT that keeps refusing) or
  at the log afterwards, and the recovery tests get a budget they cannot reach on a slow
  machine.
- **The transports are tested through fakes of the browser APIs on real web streams**, not
  only through `FakeTransport`: `MeshCoreSerial` and `MeshCoreBle` had no tests before, and
  the acceptance asks for a fake `navigator.serial` and a fake GATT device. The fakes
  implement the ambient types in `web-apis.d.ts`, so a drift between the declared API and
  the transports' use fails `npm run check`.
- **`radio.start()` is called at the end of `radio/index.ts`**, not from `main.ts`, so the
  inbox and the queue are subscribed before the first gesture-less connect fires
  `onConnected`.
- **Prettier** was run on the new files and on the touched files that were formatted before
  (`RadioPage.svelte`, `en.json`, `da.json`, `fakeTransport.ts`); `radioStore.svelte.ts`,
  `serial.ts`, `ble.ts`, `index.ts`, `TopBar.svelte`, `radioStore.test.ts` and `README.md`
  were unformatted before and are left so (P1-01 follow-up stands). Two files came out of
  the editor as CRLF and were converted back to LF before the commit.
- Candidates for `docs/decisions.md`: a lost radio link is `disconnected` with a reason, and
  the app reconnects on its own (USB: while the port is present; BLE: for five minutes);
  the transport keeps its device for the session.

## Follow-ups

- [ ] A message that is in the outbox at the moment the cable is pulled is `given_up` with
      "send failed: the companion link is closed" (P0-05's rule) and offered for retry; only
      messages still waiting in the queue resume by themselves. Re-queueing an in-flight
      message after a reconnect would need the outbox to tell a lost link from a refusal.
- [ ] No "stop reconnecting" control: the USB loop runs every 30 s while the port is present
      and `open()` fails (another program holding the port, for one). A manual Connect or
      Disconnect ends it; a button would be one call to the same cancel.
- [ ] `isKeptPort()` treats an unplug event with an unknown target as ours. Chromium always
      sets the target; the lenience is for the fakes and costs nothing with one radio.
- [ ] The Bluetooth loop's budget restarts from zero on every drop; a radio that drops every
      four minutes is retried forever. Intended (it is coming back), noted.
- [ ] The wake check sends `CMD_GET_DEVICE_TIME` on every `pageshow`, including the first
      load while disconnected (a no-op) — harmless, noted.
- [ ] Reconcile the transports against `meshguide.dk/lib/serial.js` / `ble.js` is still open
      from P0-04; this task adds the kept-device behaviour on top of the unreconciled files.
- [ ] No component tests (as before): the capability message, the reason in the top bar, the
      reconnect line and the drift line are by hand only; the decisions behind them are in
      `capability.test.ts` and the store tests.
- [ ] Prettier: the radio-layer files and `TopBar.svelte` remain unformatted (P1-01 follow-up).
- [ ] `docs/decisions.md` candidates listed under *Decisions taken*.
