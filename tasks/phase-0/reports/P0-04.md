## Decisions taken

- **`.ts`, not `.js` + `.d.ts`.** Left open by the task; CONVENTIONS.md leans `.js` "until a
  task says otherwise". Since the files are not a byte-for-byte copy anyway (see the status
  note), the reason to keep `.js` (a verbatim port, moved later) is gone, and a `.d.ts`
  beside `.js` is checked by nobody while `.ts` is checked by `svelte-check` on every verify
  — which matters most exactly for code full of byte offsets. The public names are kept,
  so the package extraction is still a move. Candidate for `docs/decisions.md`.
- **`onLog` stays a string log** (the task's lean). The store stamps each line with the
  clock and keeps the last 200 for the radio page; the console gets them too.
- **The one `new Promise` lives in `radio/deferred.ts`** with an inline eslint-disable and
  the reason in the header. The alternative, `Promise.withResolvers()`, would pass the lint
  rule unchanged but is ES2024 (`lib` is ES2023, Node 20 lacks it) and is the same thing by
  another name; hiding it would be worse than naming it. Candidate for `docs/decisions.md`
  (an amendment to the no-promise-plumbing rule: one named primitive for the transports).
- **The link owns the read loop; commands wait on a queue.** A command cannot pull frames
  itself because pushes (`MSG_WAITING`, `SEND_CONFIRMED`) must be received while no
  command runs. `sendFrame` clears stale responses so a late reply cannot be mistaken for
  the next command's; responses are queued (not single-slot) because the contact list is
  one command and many responses.
- **Device query before app start, both with protocol version 3**, so the firmware sends
  v3 message frames (with SNR) in P0-06. Older firmware answering ERR to the device query is
  tolerated (`device: null`).
- **The clock is set unconditionally with the PC time and read back**, whatever the clock
  trust. "Only moves forward" is the firmware's rule, so the log reports what actually
  happened (`moved forward`, `unchanged`, `moved back`) instead of assuming.
- **A failed identity query drops the connection**; a failed clock sync or contact list does
  not (logged, connection kept). A thing that does not answer `CMD_APP_START` is not a
  companion.
- **`blind` is only ever "connected but silent".** Unplugging the USB cable or losing BLE
  gives `disconnected`, not `blind` — walkthrough step 8 ("unplug the radio: the app says
  it is blind") will read "No radio · heard 2 s ago". If the reviewer wants the word
  "blind" there, it is a one-line change in `state()`; I read the task's definition as the
  stricter and more useful one (the cable is fine, the mesh is silent).
- **`lastHeardAt` is kept across a disconnect** and the top bar keeps showing it; the tick
  runs always, not only while connected, so the elapsed time stays live.
- **Boundary: blind when elapsed is strictly greater than the setting** ("exceeds").
- **Inbox capped at 100 pushes** (oldest dropped) so an unattended advert storm cannot grow
  it without bound while no task drains it yet; P0-05/06 consume through `onPush` and the
  inbox.
- **BLE writes without response**, one frame per write/notification, as the known-working
  implementations do; the MTU the browser negotiates has to cover a 173-byte text message
  (see *Open questions*).
- **Ambient types by hand** (`web-apis.d.ts`) rather than two `@types` packages: no new
  dependency, and only the dozen members used are declared.
- **`Contact` not widened** for the picker (it uses key and name only); the richer
  `CompanionContact` is what the store holds and the radio page shows.
- `textMessagePayload` built in this task (pure, tested) because it is a frame helper of the
  original and P0-05 names it; no sending happens here.

## Open questions

- Manual check pending (acceptance line 4): connect over USB and over BLE from the UI, the
  contact list shows, the clock sync result is logged. **Record board and firmware version
  here** (the log line `companion: "<name>" <key>…, firmware <version> (<build date>), board
  <model>, protocol <n>` has all of it).
- Layout points I am least sure of, each visible on the manual check:
  - `RESP_CODE_SELF_INFO`: three single bytes between `lon` and the frequency (offsets
    44–46), so the name starts at 57. If the name shows with a stray leading character
    or is cut, the count is wrong by one; fix `parseSelfInfo` and `selfInfoFrame` together.
  - `RESP_CODE_DEVICE_INFO`: build date at 8–20, model at 20–60, version from 60.
  - `RESP_CODE_SENT`: byte 1 is the flood flag, then expected ack, then estimated timeout.
  - Whether `CMD_APP_START`'s second byte is the same "app target version" as the device
    query's; both send 3.
- BLE: a 160-byte text message is a 173-byte write; it needs an MTU above that. Chrome on
  Windows negotiates it on most adapters, but if sends over BLE fail in P0-05 while USB
  works, switch `sendFrame` to `writeValueWithResponse` (long-write) first.
