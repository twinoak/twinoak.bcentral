## Decisions taken

- **`applyIncoming(store, incoming)` instead of the task's `applyIncoming(text,
  counterpartyId, store)`.** The roger status change must carry the incoming entry's id in
  `text`, so the function needs the stored entry, not only its text and counterparty. The
  stored entry has all three. The pure part the task asks for is `chooseRoger(rule,
  candidates)` plus `parseRoger(text)`; `applyIncoming` is the store-side wrapper that feeds
  them and appends. The rules and their order are exactly the contract's.
- **"A message this device sent" = `deviceId === store.deviceId`, any incident, any
  transport.** The contract counts `#n` per recipient per device for the lifetime of the
  register entry, across incidents; so `R2` over the radio can close a courier `#2` (the
  walkthrough has such a `#2`). Another device's `#12` is never touched: `#n` from another
  staff device is ambiguous (text-protocol.md, open point), so it is not guessed at.
- **A `message_in` is filed under the current incident; nothing is synced while none is
  selected.** The schema requires `incidentId`, and the task does not say which incident an
  incoming message belongs to. The alternatives were to hold drained messages in memory
  until an incident is picked (lost on a reload) or to invent an incident. Leaving them on
  the companion loses nothing: the firmware keeps its queue until synced, the inbox logs
  "no incident selected; messages stay on the companion", and the drain runs again on
  `onCurrentIncidentChange`. A closed incident still receives (the message is real; the
  staff can reopen or correct). Worth a line in `docs/decisions.md`.
- **Three lookups for the sender, all exact six-byte prefix matches, no guessing.** The
  companion's contact list as held (the task's rule), then the list read again (a contact
  that advertised after connect), then the register (an entry typed by hand whose radio the
  companion has forgotten). A prefix with no key or with two keys is "unknown": the message
  is logged with its text and dropped, the drain continues. The third lookup goes one step
  beyond the task's text; it costs one `getAll` and saves a message. Flagged under
  *Follow-ups* in case the reviewer wants it out.
- **The unknown-sender label goes through `t()`** ("unknown <prefix>" / "ukendt <prefix>"),
  like P0-03's "radio #n". Same consequence as before: the stored label is in the UI language
  at the time.
- **Dedupe is checked before the write** (`entryByDedupeKey`) as well as inside it (the
  store's own check in `appendEntry`), so the inbox can count and log a duplicate and skip
  `applyIncoming` for it. A duplicate never reaches the roger rules, so a redelivered `R1`
  cannot close a second message.
- **`PUSH_CODE_MSG_WAITING` only triggers; it is not parsed.** The push carries no payload
  the drain needs, and the drain reads until the companion says empty, so one push for three
  messages, or three pushes for one, both end in the right state.
- **Overlapping drains coalesce** (one run, a flag for "go round again") rather than queue,
  so two pushes in a row cost one extra sync, not a full second pass each, and the link never
  sees two interleaved sync sequences. The link's own lock would serialise them anyway; the
  flag is about not doing the work twice.
- **A storing failure for one message does not stop the drain** (logged, counted as skipped).
  Once `CMD_SYNC_NEXT_MESSAGE` has answered, the companion has dropped the message; the
  choice is between losing that one or that one and all behind it.
- **`onCurrentIncidentChange` is a listener set, not a Svelte effect.** A first version used
  `$effect.root`; under Vitest's node environment Svelte resolves to its server build, where
  effects never run, so it could not be tested. Plain listeners behave the same in the app
  and in tests, and the holder already has one write path to call them from.
- **`onConnected` on the radio store** rather than the inbox polling `link()`: the inbox has
  no reason to know when a connect finished, and the outbox pattern (`onPush` fan-out on the
  store) is already there.
- **The journal placeholder shows entries** (all types, not only `message_in`), since a roger
  is only visible as the `status_change` next to the `message_in` that caused it. The table
  is the smallest thing that lets the manual check be done; P0-07 replaces it.
- **The `delivered`-style detail on the roger status change** is the incoming id, as the
  contract and the walkthrough say — not the text `R1`. The screen shows the id; P0-07 can
  resolve it to the message.
- Prettier was run on the four new files only; the touched P0-02 to P0-05 files were already
  unformatted before this task and were left so to keep the diff readable (`npm run format`
  rewraps 11 files).
