- `store/journalStore.ts` (P0-02 file) — `appendMessageOut(input, compose)`: reads the
  recipient's counter, calls `compose(n)` for the text, validates and stores the `message_out`
  and moves the counter to `n`, all in one `entries` + `meta` transaction. If `compose`
  throws (too long), the transaction is aborted and the counter is untouched, so a refused
  send leaves no gap in `n` (P0-02's follow-up about predicting the prefix is thereby moot:
  the check runs against the number actually reserved). The body of `appendEntry` moved into
  a private `writeEntry(entries, meta, input, timestamp, clockTrust)` that both use;
  `appendEntry` itself is unchanged in behaviour.
- `store/types.ts` (P0-02 file) — `NewMessageOut` (incidentId, operator, transport,
  counterpartyId): a `message_out` before its `#n` exists.
- `store/outgoing.ts` — the text rules and the store-side flow:
  - `MAX_MESSAGE_BYTES = 160`, `byteLength(text)` (UTF-8), `seqNoPrefix(n)` → `"#n "` (whole
    number ≥ 1, one space), `composeText(n, body)` → `"#n <trimmed body>"`, throwing
    `EmptyMessageError` or `MessageTooLongError` (161 bytes is refused here; this is the
    store-path refusal the acceptance asks for), `previewText(lastSeqNo, body)` for the

    `{ message, pending }`: `appendMessageOut` with `composeText`, then for `mesh` a
    `status_change` → `pending`; for `phone` / `courier` / `verbal` no `pending` entry (see
    *Decisions*).

    moves; used by the outbox and the manual buttons.

    `recordManualStatus(store, message, newStatus, { operator, text? })`: refuses a mesh

- `radio/radioStore.svelte.ts` (P0-04 file) — `onPush(listener) → unsubscribe`: a listener
  set fed from the link's `onPush`, so a subscriber survives a reconnect and a listener that

- `radio/outbox.svelte.ts` — `createOutbox({ store, link, onPush, now, maxAttempts, operator,
  ackWindow?, responseTimeoutMs?, log? })` → `Outbox`:
  - `send(messageId)` → `Promise<"delivered" | "given_up">`. Checks before queuing: the id
    is a `message_out`, transport `mesh`, derived status `pending` or `given_up`, recipient in
    the register; a second `send` of an id already in hand is refused synchronously
    (`OutboxError`). Then **FIFO**: the caller waits for the lock (`acquire` / `release`, the
    `CompanionLink` pattern), the status is re-checked after the wait, then `transmit`.
  - `transmit`: no link → `given_up` ("no radio connected"). Otherwise subscribe to acks
    *before* the first command (so an ack in the same tick as `RESP_CODE_SENT` is not
    missed), take the timestamp, then for `attempt = 0 … max−1`: a `note` "resend #n,
    attempt k/max" referring to the message for every attempt after the first;
    `textMessagePayload(publicKey, text, { txtType: TXT_TYPE_PLAIN, attempt, timestamp })`
    through `companionCommand([RESP_CODE_SENT])`; `RESP_CODE_ERR` → `given_up` with
    "companion error <code>"; a timeout or a closed link → `given_up` with "send failed:
    <message>"; `parseSent` → on the first accepted attempt of this sequence a
    `status_change` → `sent`; wait for `expected_ack` within `ackWindowMs(est_timeout_ms)`;
    ack → `status_change` → `delivered` with "round trip <ms> ms" in `text`; no ack → next
    attempt with the **same timestamp**. After the last → `given_up` "no ack after N
    attempts". `active()` exposes `{ messageId, seqNo, attempt, maxAttempts, phase
    (preparing / sending / awaiting_ack), expectedAck, deadlineMs }` while in flight,
    `queued()` the ids waiting, `revision()` a counter bumped after every journal write (the
    screen reloads on it), `lastTimestamp()` for tests.
  - `ackWindowMs(est) = clamp(est + 2000, 5000, 20000)`; constants exported.
  - `nextTimestamp(link)`: see the status note. One `CMD_GET_DEVICE_TIME` per link, cached by
    link identity; `lastTimestamp` is kept for the session.
  - Manual retry is the same `send()` on a `given_up` message: same `seqNo`, same
    `message_out`, attempts from 0 again with a fresh timestamp, `sent` recorded again.

## Decisions taken

- **Proceeded although P0-02 to P0-04 are not merged** (status note). Same call as P0-03 and
  P0-04, same flag; not a precedent.
- **`#n` is reserved in the same transaction as the `message_out` write**, in the store
  (`appendMessageOut`), not by `nextSeqNo()` followed by `appendEntry`. The task says
  "persisted before sending" — it is persisted before the radio is touched. The transaction
  gives both things the task and P0-02's follow-up wanted: no two messages with one number,
  and no gap when a send is refused for length. `nextSeqNo()` stays for callers that want a
  bare reservation; nothing uses it now.
- **No `pending` entry for non-mesh messages.** `pending` is "queued in the app, not yet
  handed to the radio" (text-protocol.md); a courier message is never handed to a radio, and
  `contract/examples/walkthrough.json` records the courier message with `sent` as its first
  status change. The derived status of a message with no `status_change` is `pending`
  anyway, so the screen reads the same.
- **The `delivered` status change carries the round-trip time** ("round trip 800 ms") in
  `text`. The schema allows `text` on a `status_change`; the acceptance asks the reviewer to
  record the round trip from `parseAck`, and the journal is the place where it is not lost.
- **Resends are a `note` with `refersTo`**, as the task says; `sent` is recorded once per
  attempt sequence (on the first accepted transmission), not per resend. A manual retry is a
  new sequence and records `sent` again, which is the protocol's "back from given_up to
  sent".
- **Any failure before an ack is `given_up` with the reason in `text`**: `RESP_CODE_ERR`
  (the task's case), but also no `RESP_CODE_SENT` within the response timeout, a link that
  closed mid-send, a failed clock query, and no radio at all ("no radio connected"). The
  alternative — rejecting `send()` and leaving the message `pending` — would leave an entry
  that looks queued but is not. `given_up` is visible, has Retry, and says why.
- **Ack margin 2 s** on top of `est_timeout_ms`, before the 5–20 s clamp; the task names
  the clamp but not the margin.
- **Acks are collected from before the command goes out**, not from after `RESP_CODE_SENT`.
  With a fast companion (and the fake one) the ack follows the SENT response in the same
  read-loop pass; subscribing afterwards would miss it. The collected list is kept for the
  whole attempt sequence, so an ack for attempt 1 that arrives during attempt 2's window
  still counts (the expected ack is the same for a resend with the same timestamp).
- **Journal texts the outbox writes go through `t()`** ("resend #1, attempt 2/3",
  "companion error 6", "no ack after 3 attempts", "round trip 800 ms", "no radio
  connected"), consistent with P0-03's register note. Same consequence: the stored text is
  in the UI language at the time; tests pin English. P0-03's open question about
  language-independent journal text now covers two tasks.
- **A send screen with an incident row.** Nothing in the UI sets the current incident until
  P0-07, and a `message_out` needs an `incidentId`, so without it the task could not be
  exercised by hand and the manual acceptance line could not be done. The row (select over
  incidents, create by name) is the smallest slice of P0-07's incident bar; it uses the
  `lib/currentIncident` holder P0-03 made, writes through the store's `createIncident`, and
  is meant to be deleted when P0-07 lands. Flagged under *Follow-ups*.
- **`maxSendAttempts` is a saved setting** (1–10, default 3) rather than a constant, since
  the task says "(setting)"; the outbox reads it per send.
- **The Send button is disabled for `mesh` while the radio is not connected** (state
  `disconnected` or `connecting`; `blind` still allows it, since the cable is fine and the
  radio decides). Without this the message would be stored and given up at once with "no
  radio connected", which is correct but pointless when the operator can see the radio is
  not there.
- **A `pending` mesh message that nobody is sending gets a Send button** (not only
  `given_up` a Retry). After a browser reload mid-flight the message is `pending` or `sent`
  with no outbox state; `pending` ones can be sent from the list. `sent` ones cannot (see
  *Follow-ups*).
- **Push fan-out lives in the radio store** (`onPush`), not on the link, so the outbox does
  not care which link is live. The link's `inbox` is still not drained by anyone; P0-06
  decides (P0-04 follow-up stands).
- **`.svelte.ts` for the outbox** because its queue, active send and revision are rune state
  the screen renders, as `radioStore.svelte.ts` is.
