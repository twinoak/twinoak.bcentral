## Done

The data layer under `app/src/store/`, the clock module, a settings control, a journal
placeholder screen with the export button.

- `store/types.ts` — hand-written TS shapes of the contract objects (`Incident`,
  `RegisterEntry`, `JournalEntry`, `Envelope`, `ClockTrust`, `Status`, …) plus the input
  shapes `NewJournalEntry` / `NewIncident` / `NewRegisterEntry` (everything the store does
  not assign itself) and `Clock` / `ClockReading`.
- `store/schema.ts` — `contract/journal.schema.json` imported directly (no copy) and compiled
  once with `ajv` (2020-12 draft, `ajv-formats` for `date-time`). Four validators:
  `validateEnvelope`, `validateIncident`, `validateRegisterEntry`, `validateJournalEntry`, each
  a `$ref` into the contract's `$defs`. `assertValid()` throws `ValidationError` (message
  names the object kind and the schema file, `errors` carries ajv's list).
- `store/db.ts` — the `idb` layout: object stores `incidents`, `register`, `entries` (keyPath
  `id`) and `meta` (out-of-line string keys). Indexes on `entries`: `by-incidentId`,
  `by-counterpartyId`, `by-refersTo`, `by-dedupeKey` (unique). Meta keys: `deviceSeq` and
  `seqNo:<counterpartyId>`.
- `store/journalStore.ts` — `openJournalStore({ name, deviceId, clock })` → `JournalStore`:
  - `appendEntry(input)`: the single entry write path. In one readwrite transaction over
    `entries` + `meta`: dedupe lookup for a `message_in` with a `dedupeKey` (returns the
    existing entry, stores nothing), then assigns `id` (monotonic ULID), `deviceId`,
    `deviceSeq` = meta + 1, `timestamp` + `clockTrust` from the clock, strips
    `undefined`-valued fields, validates, `add`s the entry, writes the counter. Validation
    failure aborts the transaction and throws; the counter is untouched. No update, no
    delete.
  - `putIncident` / `putRegisterEntry`: validate, then `put` (insert or replace by id).
    `createIncident` / `createRegisterEntry` mint `id`, `createdAt`, `clockTrust`,
    `createdOnDevice` and go through the same `put`.
  - counters: `lastDeviceSeq()`, `lastSeqNo(counterpartyId)`, `nextSeqNo(counterpartyId)`
    (atomic reservation on `meta`). `appendEntry` of a `message_out` raises the recipient's
    counter to its `seqNo` if higher, so the counter never falls behind what was sent.
  - queries: `getEntry`, `allEntries` (id order), `entriesForIncident`,
    `entriesForCounterparty`, `entriesReferringTo`, `entryByDedupeKey`, `statusOf(id)`;
    `getIncident`, `allIncidents`, `getRegisterEntry`, `allRegisterEntries`; `close()`.
  - `exportEnvelope()`: the three arrays read in one readonly transaction, wrapped in
    `{ format, version, deviceId, exportedAt }`, validated before it is returned.
  - `importEnvelope(envelope)` (tests only for now): validates the whole envelope first,
    then writes everything in one transaction (`put` for incidents/register, `add` for
    entries), so a duplicate id or dedupe key leaves the store untouched. This device's
    counters catch up with the highest `deviceSeq` / per-recipient `seqNo` among its own
    imported entries; other devices' entries do not move them.
- `store/status.ts` — `statusOf(entries, messageOutId)`: `newStatus` of the latest
  `status_change` referring to the message, latest by timestamp (compared as instants), then
  `deviceSeq`, then `id`; `pending` when none. `latestStatusChange()` is exported too (it also
  answers "is the incident closed").
- `store/dedupeKey.ts` — `dedupeKey(senderPublicKey, senderTimestampSeconds, text)`:
  SHA-256 (WebCrypto) over `"<key>:<seconds>:<text>"` as UTF-8, lowercase hex. Throws on a key
  that is not 64 lowercase hex or a timestamp that is not a non-negative integer. `dedupeInput`
  exposes the string for tests.
- `store/export.ts` — `envelopeFilename()` → `bcentral-journal-<deviceId>-<timestamp>.json`,
  `envelopeJson()` (pretty-printed, trailing newline), `downloadEnvelope()` (Blob + temporary

- `store/index.ts` — the app's store: database `bcentral`, `settings.deviceId`, the session

## Decisions taken

- **Meta counters are not written as entries** (left open; lean no, taken). `deviceSeq` is the
  max of this device's own entries and each `seqNo` counter the max over its `message_out`s to
  that recipient, so both are reconstructible; `importEnvelope` does exactly that
  reconstruction. An entry per counter tick would double the journal for no information.
- **`appendEntry` does not assign `#n`.** The roadmap gives "`#n` assignment per recipient per
  device" to P0-05, and the number has to be known before the text (`#<n> <text>`) exists, so
  it cannot be minted inside the write of that text. The store offers the primitive:
  `nextSeqNo()` is an atomic reservation on `meta`, `lastSeqNo()` lets P0-05 predict the
  prefix for the 160-byte check before reserving, and `appendEntry` keeps the counter ≥ any
  `seqNo` it stores. Nothing in the data layer parses or formats message text.
- **Dedupe is checked only for `message_in`** (the schema forbids `dedupeKey` on every other
  type, so validation catches the rest) and the `by-dedupeKey` index is **unique** as a second
  line of defence; the contract says no other device ever hears the same direct message, so
  two entries with one key are always a duplicate delivery.
- **`statusOf` tie-break beyond the task's rule:** timestamp, then `deviceSeq`, then `id`.
  The third step is not in the contract; it only matters for two devices writing the same
  second with the same sequence number, and without it the answer would depend on read
  order. Proposed for `contract/text-protocol.md` (see *Follow-ups*). Timestamps are compared
  as instants (`Date.parse`), not as strings, so `+02:00` and `Z` spellings of one moment tie.
- **Dependency added beyond the stack decision: `ajv-formats`.** The schema uses
  `"format": "date-time"`; ajv 8 in strict mode refuses an unknown format, and the alternative
  is a hand-written RFC 3339 regex, which is exactly the kind of "probably" the conventions
  forbid. Candidate for `docs/decisions.md` together with the versions: `ajv ^8.17`,
  `idb ^8`, `fake-indexeddb ^6` (the last is named in CONVENTIONS.md).
- **The schema is imported from `contract/`, not copied into `app/`.** One source of truth;
  the cost is `server.fs.allow: [".."]` for the dev server (build and tests do not need it).
- **Export file name timestamp** is `exportedAt` without fractional seconds and colons:
  `bcentral-journal-01JB8…-2026-10-28T193000Z.json`. Colons are illegal on Windows; the rest
  stays readable and sorts by time.
- **`exportedAt` comes from the session clock's timestamp.** The envelope has no `clockTrust`
  field in the schema, so the trust is not recorded on the file itself; every entry carries
  its own.
- **`undefined`-valued optional fields are stripped before validation and storage**, so the
  validated object, the stored object and the exported JSON are the same thing (IndexedDB
  would keep the key, JSON would drop it, and `toStrictEqual` in the round trip would see the
  difference).
- **Clock control is a checkbox that can be unticked** (back to `unknown`); the task only
  asked for setting `manual`. An operator who realises the clock is wrong should be able to
  say so. `ntp`, once set, is not downgraded by hand. Trust is never persisted: a browser
  restart is a new session, by the task's definition.
- **`putIncident` / `putRegisterEntry` take complete objects** (validate, then upsert by id),
  with `createIncident` / `createRegisterEntry` as the minting wrappers that P0-03 and P0-07
  will call. Import uses the same `put`.
- **ULIDs from `monotonicFactory()`**, so ids minted on one device within the same
  millisecond still sort in creation order.
- **`importEnvelope` lives on the store** (it needs the transaction), marked tests-only in its
  comment; it is strict (`add`, not `put`, for entries) and all-or-nothing.
- **Export is pretty-printed** (two spaces, trailing newline) like the walkthrough, so the file
  is readable without tooling.
