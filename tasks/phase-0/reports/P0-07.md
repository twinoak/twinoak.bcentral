## Decisions taken

- **The task was inferred** (note at the top): the prompt had no task section. Same
  reasoning as P0-06's session; worth fixing in `run-all.ps1` (see *Follow-ups*).
- **The Send page is deleted, not kept beside the journal screen.** The task's scope does not
  name it, but `FOLLOWUPS.md` carries a reviewer fix-next for P0-07 to absorb it, and the
  runbook defines fix-next as "fix in the next task that touches it". The journal screen is
  the one the staff live on; a second screen with a second incident picker would have been
  two places to send from. `#/send` still resolves (to the journal).
- **The three P0-07 fix-nexts in `FOLLOWUPS.md` are taken** (dead placeholder key / flag,
  Send page absorption, `recordManualStatus` reconciliation). The note about
  `RegisterForm.svelte` warnings is left as the reviewer wrote it.
- **A manual status change always needs a reason, on every transport.** The task says "with a
  required reason text"; P0-05 had it optional for non-mesh. One rule is simpler than two and
  the journal should say why a human moved a status. The P0-05 test that relied on an empty
  reason was changed; nothing stored by P0-05 is affected (it is a new write-time rule).
- **On a mesh message the operator may give up or record a roger; `sent` / `delivered` stay
  the radio's** — exactly the fix-next's wording. `given_up` is the way out for a message
  stuck at `sent` after a reload mid-flight (P0-05 follow-up); `roger` covers "Hans rang".
  The screen hides Set status while the outbox holds the message, so the two writers do not
  cross; the store itself does not know about the outbox (see *Follow-ups*).
- **"Last heard from" is over the whole journal, not the incident.** The brainstorm calls it
  "communication status per radio"; a radio heard yesterday in another incident is "heard
  20 h ago", not "never". One `getAll` per reload; fine at phase-0 size. Never-heard sorts
  above the oldest contact: it is the quietest.
- **A non-mesh `message_in` is not run through the roger rules.** The contract's incoming
  rules are "the in-message protocol … inside the text of MeshCore direct messages". A roger
  that comes by phone is a manual status change on the message it answers, with the call as
  the reason — the same chain, set by hand, as `text-protocol.md` says for non-mesh. A test
  pins it (`R1` by phone stays a message).
- **Close / reopen take an optional reason**, since the task says "a `status_change` on the
  incident" and the walkthrough's closing entry has one; nothing says required. Entries can
  still be added to a closed incident (P0-06 files incoming messages there too); the bar says
  it is closed and offers Reopen.
- **Nesting is by referent presence, not by type alone.** A `status_change` whose `refersTo`
  is the incident id, or an entry outside the loaded list, is a top-level row; the
  walkthrough's incident close therefore shows as its own row at the bottom, as it should.
- **The roger's `text` (the incoming entry's id) is resolved to that entry's text** when it is
  in the incident, with a link to it; otherwise the id is shown as is. Exact id lookup, no
  matching.
- **Clock-trust mark**: `~` for `manual`, `?` for `unknown`, nothing for `ntp`, each with the
  existing `settings.clockTrust.*` sentence as its title. Phase 0 never reaches `ntp`, so
  today every row carries a mark; that is the task's rule ("when not `ntp`").
- **Correction is allowed on any row, children included** (a wrong manual status change can be
  corrected); the store accepts any stored entry as target.
- **The derivations live in `store/journalView.ts`, not in the components**, so the acceptance
  ("renders the walkthrough with correct nesting and status chips", "derived live") is tested
  without a DOM: Vitest runs in node, where Svelte resolves to its server build (P0-06's
  finding). The components are thin over those functions. No component-level tests, as in
  every task so far.
- **Prettier was run on the twelve new files only**; the touched P0-02 to P0-06 files were
  left unformatted to keep the diff readable (the open follow-up about one `npm run format`
  commit stands).

- [ ] The prompt of this run lacked its `--- TASK ---` section, as P0-06's did. Two runs in a

      has to guess its task is one step from doing the wrong one.
- [ ] `home.placeholder` still says "The journal comes in a later step"; the home screen could
      now point at the journal or go away.
- [ ] Linking a `vedr. #12` reply to #12 by hand (P0-06 follow-up): the contract says it
      "records a `refersTo` on the incoming entry", but entries are immutable
      (`CONVENTIONS.md`), so it has to be a new entry (a `note` or `correction` with `refersTo`)
      or a contract change. Decide before building it.
- [ ] `recordManualStatus` does not know about the outbox: the screen hides Set status while
      a message is in flight, but a manual `given_up` from a second tab would be followed by
      the outbox's own `sent` / `delivered`. Either the outbox re-derives status before each
      write, or the store exposes "held by the outbox". Low risk with one PC.
- [ ] The timeline renders every entry of the incident; a long drill (hundreds of entries)
      will want the list windowed or paged. Out of scope here (no filtering beyond incident).
- [ ] The `send.*` key namespace is now used by the journal screen's compose form, the
      status buttons and the outbox texts; rename to `compose.*` / `outbox.*` when a quiet
      moment allows (every key is a UI string, so the i18n test keeps it honest).
- [ ] P0-08 should reuse `OpenItemsPanel`'s chip and the page's `inflight()` text, and get
      the queue countdown from `outbox.active().deadlineMs`; the journal screen's Open items
      is the per-recipient view the roadmap asks the queue screen to have.
- [ ] No component-level tests (as before): auto-scroll, the inline forms, the panel sort and
      the in-flight chip text are exercised by hand only. A `jsdom`/browser-mode Vitest
      environment would allow it; adding one is a dependency decision for the report.
- [ ] `nextSeqNo()` in `journalStore.ts` still has no caller (P0-05 follow-up).
- [ ] `docs/decisions.md` candidates from this task: a manual status change always carries a
      reason; on mesh only `roger` and `given_up` can be set by hand; non-mesh incoming
      messages are not parsed for roger; "last heard from" spans incidents.
- [ ] Prettier: the touched P0-02 to P0-06 files are still unformatted (`npm run
