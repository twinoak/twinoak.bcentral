## Follow-ups

What the rerun of P0-08 can stand on once P0-02 to P0-07 are on `main`. None of it needs a
contract change; all of it was checked against the working tree on 2026-10-28.

- [ ] The one-at-a-time sender exists: `radio/outbox.svelte.ts` exports `createOutbox` with
      `send(messageId)` (FIFO, waits its turn, resolves `delivered` | `given_up`),
      `queued()`, `active()` (`attempt`, `maxAttempts`, `phase`, `deadlineMs`) and
      `revision()`. P0-05's own follow-up says where the rate limit goes: around the outbox,
      not inside it. A send-to-all queue is then a loop that awaits `outbox.send(id)` per
      recipient and `await`s a gap timer between calls; the countdown on the queue screen is
      `nextTransmissionAt - now` from that loop, and `deadlineMs` while an ack is awaited.
- [ ] "All `message_out` entries appended before the first transmission" is one loop over
      `composeMessage(store, …)` (`store/outgoing.ts`) per recipient before the first
      `outbox.send`. Each call reserves that recipient's own next `seqNo` inside the write
      transaction (`appendMessageOut`), so the batch needs no new store API. The batch id is
      the array of message ids the loop collected, kept in the queue module's rune state.
- [ ] "Byte counter uses the longest `#n ` prefix among the chosen recipients" is
      `previewText(max(lastSeqNo(id) for chosen), body)` with the existing `lastSeqNo` wrapper
      in `store/index.ts`; `composeText` still refuses per recipient at write time, so a text
      that fits the longest prefix fits all.
- [ ] Re-queue on start: `entriesForIncident` + `statusOf` (`store/status.ts`) gives the
      mesh `message_out` entries whose derived status is `pending`; those are the ones with
      no `sent` yet. Nothing has to be persisted for the queue, as the task says. The
      `given_up` ones are the "retry individually or all" set; both call `outbox.send` again.
- [ ] The gap setting fits `lib/settings.svelte.ts` next to `maxSendAttempts`: a positive
      integer in seconds, default 10, loaded through the same `positiveInteger` fallback, with
      a field on `pages/SettingsPage.svelte` and keys in both `en.json` and `da.json`.
- [ ] For the 25-recipient acceptance test, `test-support/companionFrames.ts` has
      `scriptedCompanion` with `onSendText(sent, index)` and `deliveredReply` /
      `sentOnlyReply`; `decodeTextMessagePayload` reads the recipient's key prefix back, which
      is how "acks mark the right recipient" is asserted. The gap must be injectable
      (`gapMs` in the queue's deps, as `ackWindow` is in the outbox's) or the test takes
      25 × 10 s.
- [ ] Open point the task leaves to the rerun: a recipient whose `given_up` came from
      "no radio connected" (P0-05 gives up at once without a link) will give up 25 times in a
      row at the gap rate. The queue should probably pause while `radio.state` is
      `disconnected` rather than burn through the batch; not decided by any contract text.
