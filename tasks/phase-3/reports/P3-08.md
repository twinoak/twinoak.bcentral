## Done

The operator is never stuck with a radio message they can neither confirm nor give up. Mark
is hidden only while the radio is in the middle of transmitting the message; a message
waiting in the send queue — also while the queue is paused because no radio is connected —
offers Mark, and marking it confirmed or given up takes it out of the queue first, so a
reconnect never sends it. A message sent from the MeshCore tab with no radio connected now
waits in that paused queue instead of being refused.

- **`lib/sendState.ts`** (new, pure): `inflight` split into the task's two facts as one rule
  over the outbox and the queue — `sendStateOf(messageId, { active, outboxQueued,
  queueWaiting, queueSending })` is `"transmitting"` (the outbox's active send for the
  message in phase `sending` or `awaiting_ack`: the radio has the payload, the ack is
  awaited), `"waiting"` (in the send queue, paused or not; handed to the outbox but not yet
  on the air — queued there or `preparing`), or `null`. **`radio/outbox.svelte.ts`**:
  `TRANSMITTING_PHASES` and `isTransmitting(active, id)` are the one definition.
- **`lib/rowActions.ts`**: `MessageActionInput.inflight` is gone; `sendState` replaces it.
  Mark is offered on a radio message until it is confirmed and hidden only while
  `sendState === "transmitting"`; Retry / Send only while `sendState === null` (a waiting
  message has nothing to retry yet). `components/Timeline.svelte` takes a `sendState` prop
  beside `inflight` (the column's words are unchanged: "waiting for its turn" or the outbox's
  phase in the slot tooltips, P3-03) and feeds the rule from it; a batch's "Retry all given
  up" counts only given-up recipients nobody holds. The open row of a waiting mesh message is
  the point action, Mark, Correct — no Retry, no Send.
- **`radio/outbox.svelte.ts`**: `cancel(messageId)` — a send waiting its turn, or preparing
  (the companion's clock not yet read), is let go: its `send()` resolves `null`, nothing is
  written, the message is free to be sent again later; a transmitting send is refused with
  `OutboxError` (`send.error.transmitting`); an id the outbox does not hold is `false`.
  `send()` is `Promise<Status | null>` now (null = cancelled). `transmitting(messageId)` for
  the screens. The waiting-its-turn case wakes every waiter on a cancel (`wakeWaiters`), so
  the cancelled one leaves without the lock at once and the rest go back to waiting.
- **`radio/sendQueue.svelte.ts`**: `cancel(messageId)` — a waiting message leaves the waiting
  list (its batch keeps the row: the queue screen shows the mark; the loop goes on with the
  rest); one the queue handed to the outbox is cancelled there; one the queue does not hold
  is `false`. The loop re-reads its head after every wait (the gap, the pause) and starts over
  when the head changed, so a cancelled head is never handed over; the pause ends when nothing
  is left waiting (the queue goes idle instead of staying paused on nothing), and a cancel
  wakes the loop. `requeuePending` is untouched: a marked message is no longer pending.
- **`radio/sendActions.ts`** (new, a factory like the outbox and the queue): what the screens

## Decisions taken

- **The MeshCore tab sends without a radio.** Acceptance line 1 ("Radio disconnected, one
  message sent from the MeshCore tab … reconnecting the radio does not send it") cannot be
  met by the app as it was: Send was disabled without a radio, and a direct send through the
  outbox gives up on the spot with "no radio connected". So a single send with no radio goes
  into the send queue as a batch of its own, which pauses until a radio connects — the same
  path Send to all already took — and the form's "no radio" line became a warning saying so.
  The outbox's own "no radio → given up" stays for a link that drops between the check and
  the send. Flagged for `docs/decisions.md`; see *Open questions*.
- **Transmitting is `sending` and `awaiting_ack`; `preparing` is waiting.** The task defines
  transmitting as "the radio has been handed the payload and an ack is awaited"; in
  `preparing` the outbox is reading the companion's clock and nothing has gone to the radio,
  so a cancel there returns before the first command. The window is a few milliseconds and
  only on the first send per link, but the rule reads as the task says.
- **A cancelled send resolves null** rather than throwing: the pages and the queue await
  `outbox.send()` and show a thrown error as "Could not send" / a refusal on the queue
  screen, which a mark by hand is not. `Promise<Status | null>` says it in the type; the
  queue logs "cancelled".
- **`sendActions` is a factory in `src/radio/`**, not functions on `store/index.ts`: the
  cancel needs the outbox and the queue, which the store must not import (the radio imports
  the store). The two store wrappers moved there whole, so there is one path for a manual
  status and a source test holds the screens to it.
- **The cancel runs before the store's write**, so a refused write (an empty reason, a roger
  already final) leaves the message out of the queue, pending, with Send on its row. The
  Mark and Close forms disable their buttons on an empty reason and Mark is hidden on a
  confirmed row, so the case is not reachable from the screen; the test says what happens.
  The other order (write, then cancel) could let the queue hand a just-marked message to the
  outbox between the two. Noted under *Follow-ups*.
- **The queue's `cancel` does not reach into the outbox for a message it never held**: a
  single send is the outbox's own, so `sendActions.cancel` asks both, in that order. The
  task's two names are both there.
- **The batch keeps the marked recipient's row** (the task: "shows the recipient as
  marked"): only the waiting list changes, and the queue screen's chip reads the derived
  status — roger or given up — once the message is no longer waiting.
- **The handover hides Close and Send by courier while transmitting**, on the same rule as
  the journal's Mark; the task says the handover's list is "unchanged, but it must use the
  same cancel path", and without the gate a Close during a live retry would reach the refusal
  as an error line. "Give up all waiting" does not exist on the queue page or the handover
  (there is "Retry all"; the handover's given-up list closes with roger, one row at a time),
  so there was nothing else to reroute.
- **The card's n counts the card's own items** waiting in the queue, not the queue's whole
  waiting list, which may hold another incident's restored messages; the line is shown only
  when n > 0.
- **A capture was added** though the task's Verify does not list `npm run screenshots`: the
  seeded run has no radio, so the queued state is on every journal capture anyway, and the
  measurement run is the one check of the row heights. The set was regenerated whole.
- **Prettier** run on every touched file that was formatted on `main` and on the four new
  files; `README.md`, `store/index.ts`, `outbox.svelte.ts`, `outbox.test.ts` and
  `docs/design.md` were unformatted on `main` and are left so (the P1-01 follow-up stands).
  Every changed file is LF.
- Candidates for `docs/decisions.md`: a radio message sent with no radio connected waits in
  the queue (the MeshCore tab does not refuse it); Mark is hidden by a live transmission
  only, and marking takes the message out of the queue.
