## Decisions taken

- **A radio is a key with an origin, nothing else.** `hasRadio` is the one definition
  (`publicKey !== undefined && origin !== undefined`) and every radio path narrows on it; the
  schema guarantees the two travel together, so a `publicKey` alone would be a stored object
  the schema refused, which cannot exist. The filter on the register screen tests the key
  alone (`matchesRadioFilter`), which is the same set.
- **The form's rule is a pure module** (`lib/registerForm.ts`), as P3-01…P3-05 did for
  theirs: "the form must not be able to produce the invalid shape" is a rule, so it is a
  function with a test, not a `$derived` that only a browser exercises. The origin select
  keeps `issued` while disabled, so a key pasted later has an origin at once ("edit, paste
  key, pick origin" works without picking when issued is right).
- **The Radio section is a `div role="group"` with a heading span**, not a `fieldset`: a
  fieldset's default border would need `border: 0` in the component's style block, which
  docs/design.md forbids (the sources test caught it).
- **Origin left the table; phone and radio took its place.** The task's column list has no
  origin, and the glyph + prefix cell says "has a radio" better than a word; the origin is
  the cell's tooltip with the full key, and the form has it.
- **The handover's status request is refused at the store too** (`assertRadioRecipient` in
  `composeStatusRequest`), not only hidden by the quiet-radios list: the task says "only for
  entries with a key", and a store path that would compose a mesh message to a keyless
  contact contradicts the contract. `composeBatch` was left as it is (P3-01's decision: it
  composes to ids without a register lookup, and 15 tests rely on that); the send-to-all
  form hands it radio contacts only. Flagged under *Follow-ups*.
- **The CSV import is `createRegisterEntries`.** With no pending rows the import's write is
  the batch's write (validate all, one transaction, all or nothing); `importRegister` on the
  store would have been the same function under a second name.
- **Empty `origin` on a keyed row is still `issued`** (P1-06's rule), and an `origin` on a
  keyless row is an error rather than ignored: the task says "reported as an error", and
  silently dropping a word the resident list carries would hide a key that was forgotten.
- **The import note counts the radios** ("imported 5 contacts from beboere.csv, 2 with a
  radio") instead of the old "3 not yet bound": there is nothing to bind, and what the
  journal reader wants to know is how many of the new contacts can be reached on the mesh.
- **"Kommunens vagt" is a contact** in the seed, with a phone and a role: the duty officer
  the staff ring is exactly the person the task was written for, and the 19:43 call that was
  filed against Hans ("Kommunens vagt ringede …") belonged to them. The open point moved with
  the call.
- **Prettier** run on the new files and on every touched file that was formatted on `main`;
  `README.md`, `outbox.svelte.ts`, `index.ts`, `journalStore.ts`, `outgoing.ts`,
  `outgoing.test.ts`, `register.test.ts` and `types.ts` were unformatted on `main` and are
  left so (the P1-01 follow-up stands). `inbox.svelte.ts` came out of the editor as CRLF
  and was converted back; every changed file is LF.
- Candidates for `docs/decisions.md`: a register entry is a contact and a radio is optional
  (the contract says so since 2026-11-16; this is the app side); `origin` belongs to the
  radio and is only ever stored with a key; a CSV row without a key is a contact, not a
  pending row; the MeshCore tab, send to all and the status request take radio contacts and
  nothing else.
